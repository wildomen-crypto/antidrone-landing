## Выбор модели и расход лимитов

**Основной вариант: GPT-6.1 Sol, Medium, Standard.** Сложная часть проекта — параметрическая геометрия, согласование 3D и ведомости, много вариантов состояния и надёжная форма. Для неё лучше сохранять одну основную модель и стабильную архитектуру.

**Экономный вариант: Sol для архитектуры, геометрии и проверок; GPT-6 Luna Low/Medium для законченных небольших правок.** Luna поручать конкретный блок с понятным критерием готовности: адаптировать карточки, исправить отступы, заменить утверждённый текст, добавить материал в конфигурацию. Не отдавать экономной модели весь неопределённый проект одной фразой.

**Усиливать только сложный этап:** Sol High при неясной геометрической ошибке, проверке тарифов или взаимосвязей слоёв. Astra имеет смысл для отдельной сложной задачи, если Sol не справился; постоянно использовать её для верстки этого сайта не требуется. Это оценка для данного проекта, не универсальный рейтинг моделей.

[Официальные рекомендации OpenAI по моделям](https://learn.chatgpt.com/docs/models) и [выбору режима](https://developers.openai.com/api/docs/guides/model-selection) поддерживают Sol для сложной разработки и Luna для ограниченных задач. Высокое усилие рассуждения использует больше токенов.

Для сопоставления платных кредитов Standard, по [актуальной таблице](https://learn.chatgpt.com/docs/pricing):

| Модель | Вход, кредитов / 1 млн токенов | Кэшированный вход | Выход |
| --- | ---: | ---: | ---: |
| GPT-6 Luna | 2,5 | 0,25 | 12,5 |
| GPT-6.1 Sol | 50 | 2,5 | 250 |
| GPT-6 Astra | 250 | 25 | 1250 |

Эта таблица относится к кредитному биллингу, а не к количеству задач, включённых в Plus. Более низкая ставка сама по себе не гарантирует меньший общий расход при большом числе исправлений. API оплачивается отдельно; его долларовые ставки не использовать для оценки лимитов подписки.

[Fast](https://learn.chatgpt.com/docs/agent-configuration/speed) расходует включённые лимиты в 2,5 раза быстрее Standard, а платные кредиты — по множителю 2. Для этого проекта выбрать Standard. Непрерывные режимы максимального рассуждения и необязательная генерация множества изображений расход увеличивают.

На момент проверки аккаунта инструментом Codex доступен план Plus: использовано 2% пятичасового окна и 0% недельного; дополнительные кредиты не доступны. Это моментальный снимок, а не прогноз оставшейся ёмкости после исследования или будущей разработки.

Честная оценка: полный проект потребует нескольких сессий. План содержит 12 крупных этапов, разделённых ниже на 32 небольших блока. Один запрос на выполнение охватывает один блок; сложный блок дополнительно делится до начала существенных изменений. Первый предметный прототип охватывает этапы 1–5. Этап, блок, сообщение и окно лимита — разные единицы; завершение блока в одном окне не гарантируется. Расход оценивать по первым завершённым блокам и фактической статистике аккаунта.

## Как работать экономно

1. Создать отдельный проект; положить ТЗ в `docs/SPEC.md`, источники — в `docs/RESEARCH.md`.
2. Исследование уже проведено. Не просить модель заново изучать рынок при каждом изменении кнопки.
3. Дать короткий `AGENTS.md`: архитектура, правила геометрии, ссылка на ТЗ, команды проверок. Не копировать туда весь документ.
4. В каждом задании указывать этап, файлы/модули и критерий готовности. Просить сначала прочитать соответствующий раздел, а не всю историю.
5. До изменения кода, после законченной части блока и после проверки обновлять `docs/STATUS.md`: выполнено, проверено, нерешённое, следующий шаг. Новая сессия читает этот файл и нужные разделы ТЗ.
6. Не менять одновременно дизайн, стек, формулы и геометрию. Сначала принять данные и генератор, затем оформлять визуализатор.
7. Использовать общие примитивы и один движок для всех схем. Восемь копий калькулятора увеличат число ошибок и расход на сопровождение.
8. Хранить reference-изображения локально; обращаться к нужным страницам, а не повторно загружать все 74 страницы в каждый запрос.
9. Проверять изменения по подходящим тестам; не перезапускать многократно полный набор без причины.
10. Фиксировать проверенную рабочую версию Git после каждого блока; сохранять промежуточные результаты по протоколу ниже. Не откладывать сохранение до конца большого этапа.

Базовая разработка не требует вызовов OpenAI API из сайта. Формулы, геометрия и цена вычисляются обычным кодом. Не добавлять AI-чат и платное распознавание чертежей в первоначальный объём.

## Сохранение прогресса и восстановление после лимита

Этот протокол — требование к разработке проекта. Он использует локальные файлы и Git, а не предполагает, что модель успеет написать итог перед неожиданным обрывом. Подход с небольшими проверяемыми этапами и постоянным журналом соответствует [официальному руководству OpenAI по длительной работе Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex); конкретные правила ниже разработаны для этого сайта.

### Что сохранить в проекте с первого блока

- `AGENTS.md`: краткие постоянные правила, один блок за запрос, проверки и запрет разрушительного восстановления.
- `docs/SPEC.md`, `docs/RESEARCH.md`, `docs/CODEX_PLAN.md`: источник требований; не менять объём незаметно.
- `docs/BLOCKS.md`: ID всех блоков, статус, зависимости и критерии готовности. Начальное состояние — `TODO`.
- `docs/STATUS.md`: текущий блок, последний проверенный Git-коммит, изменённые файлы, выполненные команды, незавершённое и точный следующий шаг.
- `docs/checkpoints/<block-id>.md`: короткая карточка текущего блока; создана **до** существенных правок. Фактические команды и результаты добавляются по ходу работы.
- Git и lockfile: воспроизводимая проверенная версия. Не включать секреты, персональные данные заявок, локальную БД, сборочные каталоги и зависимости.

Готовые заготовки рядом с планом: [правила AGENTS](templates/AGENTS.template.md), [реестр 32 блоков](templates/BLOCKS.template.md), [журнал состояния](templates/STATUS.template.md), [карточка блока](templates/CHECKPOINT.template.md). Это шаблоны для нового проекта, а не отчёт о выполненной разработке. В B01.1 перенести их на указанные пути и заменить поля фактическими данными. Реестр содержит полный первоначальный перечень задач; после деления или изменения объёма обновлять его вместе с планом.

**Статусы блоков:** `TODO` → `IN_PROGRESS` → `VERIFIED`. При плановой остановке незавершённый блок получает `PAUSED`; при отсутствии необходимых внешних данных — `WAITING_EXTERNAL`. Внезапный обрыв может оставить `IN_PROGRESS`: это нормальный сигнал для аудита, а не доказательство повреждения или завершения. `VERIFIED` допускается только при выполненном результате и записанных успешных проверках.

### Порядок выполнения одного блока

1. Прочитать `AGENTS.md`, `STATUS.md`, строку блока и необходимые разделы ТЗ. Проверить текущую ветку, `git status`, последние коммиты и незавершённые изменения. Зафиксировать имеющиеся изменения пользователя; не включать их в свой коммит автоматически.
2. Записать `IN_PROGRESS`, исходный проверенный коммит, план изменения файлов, критерии и следующий шаг **до редактирования кода**. Для первого блока, когда коммитов ещё нет, указать это явно и сначала получить минимальную собираемую основу.
3. Разрабатывать в отдельной локальной ветке этапа от проверенной версии. Основная проверенная ветка и ранее размещённый сайт не меняются незавершёнными изменениями. Переключение веток выполнять только после сохранения текущих правок; не переносить их молча.
4. Делать небольшие согласованные изменения. Обновлять журнал после законченной части: создан контракт, реализован генератор, проверен сценарий. Не ждать конца всего этапа. Незавершённая функция не должна ломать запуск уже принятых функций: при необходимости подключать её после проверки или через явный флаг.
5. Запустить соответствующие проверки блока. Базово — типизация и сборка при изменении кода приложения; для формул/геометрии — контрольные тесты; для UI/3D — подходящий визуальный сценарий. Команды, дата, результат и непроверенное записываются в карточку. Если команда не завершилась, её результат — «неизвестен», а не «успешно».
6. При успешных проверках сохранить коммит только относящихся к блоку файлов и его документации. Записать SHA этого коммита в `STATUS.md` отдельным обновлением документации; не пытаться помещать SHA коммита внутрь него самого. Последний проверенный SHA относится к коду, а последующее изменение журнала — к документации. Отмечать блок `VERIFIED`, указать следующий ID.
7. Завершить запрос коротким отчётом: ID, что готово, проверки, сохранённая версия, следующий блок. Следующий блок самостоятельно не начинать. Пользователь может дать новое задание после обновления лимита или в другой сессии.

### Плановая остановка

Если виден малый остаток лимита либо пользователь просит остановиться, не начинать новую большую часть. Сохранить текущие файлы и обновить журнал: что сделано, что ещё не проверено, какие команды могли остаться в работе, какой точный шаг следующий. Незавершённые правки можно сохранить отдельным WIP-коммитом в рабочей ветке после проверки diff на секреты. **WIP не меняет последний проверенный SHA, не получает статус VERIFIED и не размещается на коммерческом сайте.**

Если Git-коммит недоступен, например не настроена личность автора, не подставлять выдуманную личность. Сохранить файлы и снимок исходников с журналом в указанном каталоге резервных копий, исключив секреты и данные заявок; отметить причину отсутствия коммита. Исправить настройку Git отдельным шагом до дальнейшей интеграции. Пока нет первого снимка и проверенной основы, не начинать большой функциональный блок.

### Внезапный обрыв и продолжение

Не рассчитывать на последнее сообщение модели: обрыв может случиться между изменением файла и проверкой. При продолжении сначала сопоставить журнал с реальными файлами, `git status`, diff и историей Git. Если журнал устарел, фактический код и результаты повторной проверки имеют приоритет; исправить запись до дальнейшей работы.

Прочитать карточку незавершённого блока, определить завершённые действия и оставшиеся. Проверить, не продолжает ли работать ранее запущенная установка, сборка или миграция; не запускать её повторно вслепую. Затем выполнить минимально необходимые проверки и закончить **этот же блок**. Не выполнять `git reset --hard`, `git clean`, удаление каталога или переустановку всего проекта как способ «начать заново». Не повторять миграцию БД без проверки её состояния; destructive-миграции не входят в обычное восстановление.

Последняя проверенная версия остаётся доступна по SHA. Если незавершённая ветка не собирается, сохранить её для ремонта, а рабочую проверенную версию открыть в отдельном каталоге/checkout без удаления текущих изменений. Резервные копии БД и конфигурации инфраструктуры нужны отдельно: Git не сохраняет работающую БД и секреты.

**Граница гарантии:** план сохраняет принятые блоки и позволяет восстановить незавершённый. Он не обещает, что любая рабочая ветка будет собираться в каждую секунду или что Codex предскажет точный момент исчерпания лимита. При обычном прерывании объём перепроверки ограничивается текущим блоком и его затронутыми зависимостями.

### Проверка протокола до запуска

В `B11.3` выполнить репетицию: сохранить карточку частично выполненного блока, завершить сессию и продолжить с чтения файлов проекта без опоры на историю чата. Подтвердить, что найден последний проверенный коммит, незавершённые правки сохранены, следующий шаг определён и завершённые блоки не переделываются. Отдельно проверить доступность проверенной версии из другого checkout. Записать результат; это проверка восстановимости, а не имитация реального исчерпания лимита аккаунта.
