## 1. Цель продукта и позиционирование

Создать простой профессиональный русскоязычный сайт компании, которая проектирует, изготавливает, поставляет и монтирует металлоконструкции для пассивной защиты гражданских и промышленных объектов от БПЛА в РФ.

Сайт должен помочь заказчику понять предложение, выбрать предварительную форму конструкции, увидеть её по своим размерам и отправить содержательную заявку. Основной результат для бизнеса — запросы на проектирование, изготовление по готовым чертежам и поставку с монтажом.

Главное сообщение: **«Защитные металлоконструкции под размеры вашего объекта. Проектирование, изготовление и монтаж»**.

Основные сценарии:

1. Нет проекта: выбрать схему, ввести размеры, посмотреть 3D, получить ориентир и отправить конфигурацию инженеру.
2. Есть проект: выбрать «Изготовление по чертежам», оставить контакт и передать документы через согласованный канал.
3. Нестандартная площадка: оставить минимальные исходные данные для консультации.
4. Нужна только часть работ: запросить проектирование, каркас, заполнение, монтаж или восстановление секций.

Аудитория: руководители предприятий, технические директора, проектировщики, специалисты по закупкам и эксплуатации. Термины раскрывать при первом употреблении: КМ — конструкции металлические; КМД — деталировочные чертежи; ЗОК — защитные ограждающие конструкции.

## 3. Объём реализации

Конечный продукт: одна коммерческая страница `/` с якорями. Служебные страницы `/privacy` и `/consent` необходимы для документов; они не превращают продукт в многостраничный каталог. После запуска SEO-страницы могут стать отдельным проектом.

### Первый рабочий выпуск

- Все блоки лендинга, адаптация, доступность, SEO и реальная обработка заявок.
- Общий движок геометрии, объёмов и цен.
- Схемы C1–C5: экран, периметр, навес, укрытие, пристенный экран/козырёк.
- Схема C8: комплекс нескольких контуров по альбомам; сначала визуализация и сбор исходных данных, без автоматической полной сметы.
- Простые стойки и пространственные опоры; балки и фермы.
- Заполнения: сетка, тросовая сеть, трубчатая решётка/покрытие; остальные показываются в каталоге и активируются после согласования производства.
- Сохранение конфигурации JSON и печатная карточка для браузерного экспорта в PDF.

### Следующее расширение до полного ТЗ

- C6 — галерея/проезд: арочная, П-образная и канатная компоновки.
- C7 — круглый контур и условное купольное укрытие.
- Комбинированные стеновые решения, более подробные узлы, сравнение до трёх вариантов, защищённая загрузка файлов.

Восемь семейств входят в конечное ТЗ. Разбиение определяет порядок разработки, а не исключает сложные формы. Первый выпуск уже должен показать фирменную схему по PDF; её нельзя заменить одной прямоугольной коробкой.

Не включать в первую версию личный кабинет, интернет-магазин, оплату онлайн, BIM-редактор, расчёт прочности, симуляцию воздействия, автоматический подбор уровня защиты или проектной документации. Эти функции не нужны для первоначальной продажи услуг.

Анимация только функциональная: подсветка выбранной поверхности и плавное изменение камеры. Без постоянного вращения, видео на автозапуске и многократных всплывающих окон.

## 7. Пользовательский сценарий калькулятора

Заголовок: «Соберите предварительную схему по размерам».

Три понятных шага в одном блоке:

1. **Конструкция**: выбор формы по иллюстрированным карточкам; вариант «Помогите выбрать».
2. **Размеры и заполнение**: по умолчанию 3–5 обязательных параметров, остальные в «Дополнительных настройках».
3. **Результат**: 3D, площади, условная комплектность, стоимость при действующих тарифах и кнопка заявки.

Компьютер: слева параметры 35–40% ширины; справа схема 60–65%; результат под схемой. Телефон: форма и переключатель «3D / Список параметров», затем результат; холст высотой примерно 300–360 px. Все основные действия доступны без полноэкранного режима.

Контакт не требуется для использования калькулятора. «Получить расчёт инженера» открывает короткую форму с уже приложенной конфигурацией.

Форма чисел: метры для габаритов и миллиметры для сечений. Поле поддерживает десятичную запятую и точку; подпись единицы видима постоянно. Пустое поле во время ввода не превращается в 0. Невалидный ввод не ломает последнюю корректную модель. Ошибка отображается рядом с полем; старый результат отмечается как неактуальный и не экспортируется как новый.

Базовые демонстрационные пределы UI: длина 1–200 м, ширина 1–100 м, высота 0,5–30 м; для C8 отдельно разрешить условную высоту до 80 м. Это диапазоны визуализатора, не допустимые производственные размеры и не рекомендации. Перед публикацией пределы заменяются диапазонами подтверждённых шаблонов. Вне шаблона пользователь сохраняет габариты и отправляет индивидуальный запрос.

Шаг секций, профили и фундаменты изначально скрыты в дополнительных настройках. Для обычного пользователя доступны только утверждённые компанией шаблоны. Внутренний режим демонстрации может принимать произвольную геометрию с явной отметкой «Схема вне типового решения».

## 8. Спецификация восьми калькуляторов

### C1. Линейный экран

Обязательные поля: длина L, высота H, заполнение. Дополнительно: шаблон секций, покрытие металла, проём, изготовление/монтаж.

В 3D: начальная и конечная стойки, промежуточные стойки, рамы, перемычки и заполнение. Размеры L/H; каждая секция в списке. Изменение L добавляет/удаляет секции, а не растягивает всю модель.

Результат: площадь заполнения, длина контура, количество секций и опор; масса только при известных профилях/паспортах. Проём убирает заполнение, но добавляет его обрамление согласно шаблону.

### C2. Прямоугольный периметр

Обязательные: L, W, H, заполнение. Дополнительно: включение сторон A–D, один проём с привязкой к стороне, калитка/ворота, покрытие.

В 3D: углы, стороны, стойки и проём. Угловая стойка общая для двух сторон. При отключении стороны соседние стойки остаются, если используются другими элементами.

Результат: активная длина ограждения, площадь заполнения, опоры и секции. Закрытый периметр не обещает наличие верхнего покрытия.

### C3. Открытый навес

Обязательные: L, W, H и покрытие. Дополнительно: простые/пространственные опоры, балочный/ферменный шаблон, существующее основание/фундамент, услуги.

В 3D: два ряда опор, ригели или фермы, прогоны/канаты, покрытие. Для M6 показать отдельные параллельные трубы, как в полном альбоме; для M5 — канаты; для сетки — полотно и несущие элементы отдельно.

Результат: пятно покрытия и площадь материала, комплект каркаса, условные основания. При превышении диапазона шаблона цена скрывается, размеры сохраняются.

### C4. Объёмное укрытие

Обязательные: L, W, H, заполнение. Дополнительно: отдельный материал покрытия и стен; стороны A–D; один сервисный проём; вид каркаса и услуг.

В 3D: несущий каркас и пять независимо переключаемых поверхностей. Трубы заполнения отличаются от труб каркаса толщиной отображения и цветом. Есть режим «Только каркас».

Результат: площадь покрытия, площадь каждой стороны, суммарная площадь каждого материала, опоры, рамы, сервисный проём. Разные материалы суммируются по собственным тарифам.

### C5. Пристенный экран / козырёк

Выбор режима: вертикальный экран или козырёк. Поля экрана: L, H, вынос D. Поля козырька: L, вылет D, отметка установки H. Дополнительно: заполнение, кронштейны, предполагаемая поверхность крепления.

В 3D: условная полупрозрачная стена, отдельные кронштейны, рама и полотно. При изменении выноса увеличиваются кронштейны и размерная линия, а стена остаётся на месте.

Результат: площадь заполнения и условная комплектность. Анкеры и допустимость крепления к зданию уточняются после обследования; автоматический выбор основания отсутствует.

### C6. Галерея / проезд

Режимы: арочная, П-образная, канатная на опорах с оттяжками. Обязательные: длина L, ширина W, свободная высота H; для арки — подъём R. Дополнительно: торцы, боковое заполнение, утверждённый шаг рам, зона оттяжек.

В 3D: повторяемые модули, соединяющие элементы, открытый проезд; оттяжки и анкеры видны вне проезда. Свободная высота измеряется до нижнего элемента конструкции, а не до вершины арки.

Результат: площадь покрытия по поверхности, площадь выбранных стен, количество рам и длина элементов. Галерея рассматривается как объект гражданской площадки. Никаких параметров атак, противодействия или оценки вероятности перехвата в UI.

### C7. Круглый контур / купольное укрытие

Обязательные: диаметр D, высота H, покрытие включено/выключено; для покрытия — подъём R. Дополнительно: секторный шаблон, боковое заполнение, сервисный сектор.

В 3D: кольцо опор и, при выборе покрытия, радиальные элементы; по центру условный объект. В интерфейсе назвать форму покрытия точно: сферический сегмент или секторное шатровое покрытие. Формулу площади выбирать по реальной форме генератора.

Результат: окружность, площадь выбранных поверхностей, количество секторов/опор, комплектность. Круглая форма не является автоматическим подбором решения для любого резервуара.

### C8. Комплексное укрытие по альбомам

Наиболее важная нестандартная схема для этого проекта. В обычном режиме поля: размеры условного объекта L0/W0/H0; количество контуров 1–3; вид несущих элементов и заполнение. В дополнительных настройках: отступ и высота каждого контура, стеновой модуль, сетка опор, демонстрационный провис, сервисный проём, тип основания.

Отступы определяются **от внешнего габарита условного объекта**, а не последовательно от соседней оболочки. UI прямо поясняет это. Контуры располагаются вокруг общей оси объекта. При одинаковых геометрических габаритах разные контуры не автоматически объединяются; объединение — отдельный согласованный шаблон.

Уточнение от 4 октября: на /wide отступ и высота каждого контура C8 —
компактные ползунки с точным вводом, как у размеров конструкции.
Пределы остаются 0,1–20 м и 0,5–80 м; проверка порядка отступов и высоты
относительно объекта сохраняется. Два поля в строке на широком экране,

## 9. Математика геометрии и объёмов

Ниже — правила коммерческой геометрии. Они не рассчитывают несущую способность, воздействия, отстояния для защиты, сечения по нагрузке или фундаменты по грунтам.

### Секции и узлы

Для прямой стороны длиной L и максимального шага схемы S: `n = ceil(L / S)`, фактический шаг `s = L / n`. Разбиение равномерное; обе конечные точки сохраняются. S берётся из визуального шаблона, не считается допустимым пролётом без инженерного подтверждения.

Для замкнутого прямоугольника без проёмов и с одинаковым шагом: `nL = ceil(L/S)`, `nW = ceil(W/S)`; секций `2*nL + 2*nW`, стоек столько же. Для произвольного набора сторон, проёмов, порталов и дополнительных опор использовать уникальные узлы графа, а не эту упрощённую формулу.

Граф: узлы с координатами, стержни с начальным и конечным узлом, поверхности, опорные сборки, комплекты узлов. Общая колонна на пересечении нескольких ферм создаётся один раз. Дедупликация — по устойчивому ID или координате с заданным допуском. Длины стержней считать из координат; дубли поясов разных сборок обрабатывать согласно шаблону, не удалять автоматически конструктивно разные элементы.

### Площади

- Прямой экран: `A = L*H - Aopenings`.
- Периметр: `A = H*(сумма активных длин) - Aopenings`.
- Плоское покрытие: `Aroof = L*W`.
- Четыре стороны прямоугольного укрытия: `Awalls = 2*(L+W)*H - Aopenings`.
- Площадь материалов по слоям: сумма по всем активным поверхностям. Два слоя — две позиции; один слой не умножать второй раз в цене.
- Наклонное, арочное или секторное покрытие: площадь реальных поверхностей генератора; плановая проекция показывается отдельно.

Для полукруглой галереи без вертикальных боковых стен: `R=W/2`, площадь криволинейного покрытия `A=π*R*L`. При наличии вертикальных стенок добавить их отдельно. Для произвольного подъёма арки использовать длину дуги из того же профиля или численную аппроксимацию. Не применять формулу полукруга ко всем аркам.

Для кругового стенового ограждения `Awall=π*D*H`; для плоского круглого покрытия `Aroof=π*D²/4`. Формула сферического сегмента допустима только при соответствующей геометрии; секторный шатёр считать по треугольникам поверхности.

### Проёмы и материалы

Проём хранить в локальных координатах поверхности: сторона, смещение, ширина, высота, отметка. Не допускаются отрицательные размеры, выход за поверхность и пересечение других проёмов. В первом выпуске один проём на схему; архитектура поддерживает список. Площадь отверстия вычитать из полотна, обрамление и воротную секцию добавлять отдельными элементами.

`Ageom` — геометрическая площадь; `Aorder` — площадь заказа по формату карт/рулонов, нахлёстам и утверждённому запасу. Выводить обе при различии. Если используется коэффициент раскроя, не учитывать те же нахлёсты второй раз. Точный раскрой на полосы/карты — отдельное расширение, не обещать его в первом выпуске.

Для трубчатого заполнения длины всех труб считать из генератора. Число параллельных элементов определяется заданным шагом визуального шаблона; крайние элементы и рамка имеют отдельные ID. Масса: `Σ(длина элемента * масса погонного метра из сортамента) + масса известных пластин/узлов`. При отсутствии данных показать «Масса уточняется», а не назначать случайную удельную массу.

Провис канатов — геометрический параметр эскиза. Кривая может быть условной параболой; длину оценивать численно по сегментам. UI не выводит натяжение и не называет форму расчётной цепной линией без отдельной модели.

### Контрольные примеры для разработчика

1. Укрытие `10×6×4 м`, плоская крыша, четыре стены, без проёмов: крыша 60 м², стены 128 м², всего 188 м².
2. Один проём `3×3 м`: стены 119 м², всего 179 м². Расход обрамления добавляется отдельно.
3. Два одинаковых слоя на всех поверхностях исходного укрытия: 376 м² материала; пятно остаётся 60 м².
4. Периметр `10×6 м`, шаг схемы 3 м: 12 секций и 12 уникальных стоек, без дополнительных воротных стоек: `2*ceil(10/3)+2*ceil(6/3)=12`. Арифметическая ошибка исходного примера (14) исправлена при реализации.
5. Прямой экран 10 м, шаг 3 м: 4 секции по 2,5 м и 5 стоек.
6. Плоский навес при изменении длины 10→20 м и неизменной ширине 6 м: площадь 60→120 м². Цена может увеличиться иначе из-за опор, минимальной партии и доставки.
7. Скрытие слоя в 3D не меняет площади заказа и цену. Исключение слоя из конфигурации меняет их.
8. Два контура с разными тарифами рассчитываются раздельно; общая мобилизация начисляется один раз на заказ, если таков тариф.

Не создавать отдельный цилиндр для каждой проволоки сетки на большой площади. Цели приёмки: обновление типовой схемы ≤200 мс после подтверждения поля на контрольном компьютере; не менее 30 FPS при вращении контрольной сцены на выбранном среднем Android-устройстве. До старта тестирования зафиксировать модель устройства, браузер и максимальный набор элементов. Ограничение DPR и детализации допускается; нельзя молча уменьшать расчётное число элементов.

## 13. Заявка и обработка контактов

Короткая форма: имя необязательно, компания необязательно, способ связи, телефон или email (хотя бы один), комментарий необязательно, отдельное согласие на обработку данных. Для запроса КП — регион и набор услуг, если не переданы из калькулятора.

Заявка прикладывает `configuration`, `configurationVersion`, `templateVersion`, `priceVersion`, `estimateMode`, исходные размеры, выбранные материалы и услуги, время и источник формы. Сервер повторно проверяет конфигурацию и пересчитывает стоимость; клиентская сумма не является доверенным источником.

Путь обработки: валидация → запись в БД → выдача ID заявки → очередь уведомления сотруднику компании. Если email/CRM временно недоступны, заявка сохраняется и отправляется повторно; UI не сообщает потерю заявки, если она уже сохранена. Если запись не произошла, показать понятную ошибку и сохранить поля. Повторная отправка с тем же ключом не создаёт дубль.

Публичная надпись «Заявка отправлена» разрешена только после подтверждения сервера. В демонстрационном режиме: «Это демонстрация формы; заявка не отправляется». Неподключённая кнопка и имитация успеха недопустимы.

Регион хранения заявок, резервных копий и файлов — РФ. CRM, почтовый сервис, аналитика и получатели данных выбираются после проверки фактической схемы обработки. Для этого ТЗ не отправлять полный комплект документов объекта через публичные мессенджеры автоматически.

В первом выпуске можно обойтись без загрузки файлов: заявка «Есть проект» и указание согласованного корпоративного канала передачи. Расширение загрузки: до 3 файлов по 15 МБ; PDF/JPG/PNG; проверка расширения, MIME и сигнатуры, антивирусный карантин, частное хранилище, случайные имена, короткие подписанные ссылки, ограничения доступа и срока хранения. CAD-файлы передаются отдельно или после специального согласования форматов.

Согласие не отмечено заранее; ссылка ведёт на отдельный текст, политика отдельно. Фиксировать версию согласия и факт действия. Рекламная рассылка требует отдельного необязательного основания/согласия и не включается в заявку. Правовые тексты и сроки хранения утверждает оператор данных до запуска.

Основание для требований: [152-ФЗ, статьи 9, 18 и 18.1](https://mintrud.gov.ru/docs/laws/130); [разъяснение Минюста о раздельном согласии](https://to19.minjust.gov.ru/ru/events/3561/). Архитектурные меры не заменяют организационные обязанности оператора.

Защита формы: серверная проверка полей и размеров, лимит запросов, скрытое антиспам-поле, защита от дублирования, проверка происхождения запросов и безопасное формирование уведомлений. Секреты CRM/SMTP хранятся только на сервере. Логи не содержат полный телефон, email, комментарии и загруженные документы.

## 14. Техническая архитектура

Рекомендуемый вариант: TypeScript, React, Next.js с серверной выдачей маркетингового контента; Three.js через React Three Fiber для одного клиентского 3D-блока. Стили — CSS Modules или один выбранный подход; не смешивать несколько UI-систем. Формы и входные данные — единая типизированная схема валидации. Подключать только необходимые зависимости.

3D загружается при приближении к блоку калькулятора/по нажатию, а первичная страница остаётся лёгкой. Основание: [официальные рекомендации Next.js по отложенной загрузке](https://nextjs.org/docs/app/guides/lazy-loading). Управление камерой сверять с [документацией Three.js](https://threejs.org/docs/pages/OrbitControls.html).

Версии выбираются и проверяются на старте разработки; фиксируются lockfile. Не записывать произвольные «последние» номера версий в ТЗ.

Слои реализации:

1. `content` — компания, услуги, кейсы и документы.
2. `catalog` — формы, материалы, совместимость и утверждённые шаблоны.
3. `geometry` — чистые функции генерации графа и поверхностей.
4. `quantities` — ведомость из того же графа.
5. `pricing` — отдельные функции тарифов; без привязки к рендеру.
6. `viewer` — отображение, камера, слои, подписи и fallback.
7. `leads` — серверное сохранение и уведомления.

Состояние формы — единственный источник параметров. `geometry` и `quantities` не должны иметь копий бизнес-правил в разных компонентах. Проверенный расчёт может исполняться и на клиенте, и на сервере.

### Схема конфигурации

```ts
type Configuration = {
  schemaVersion: number;
  shape: 'screen' | 'perimeter' | 'canopy' | 'enclosure'
    | 'facade' | 'passage' | 'round' | 'complex';
  templateId: string;
  dimensions: { length?: number; width?: number; height: number;
    diameter?: number; rise?: number; offset?: number };
  structuralSystem: string;
  surfaces: Array<{ id: string; enabled: boolean; materialId: string;
    layers: number; openings: Opening[] }>;
  contours?: Array<{ id: string; enabled: boolean; offsetFromObject: number;
    height: number; templateId: string; surfaces: string[] }>;
  foundationTemplateId?: string;
  services: string[];
  regionId?: string;
};
```

Виды C5–C8 имеют расширение схемы для своих параметров; использовать discriminated union или эквивалентную строгую валидацию. Невозможные поля разных форм не переносятся молча. Числа конечные и положительные по смыслу. `viewState` с видимостью слоёв хранить отдельно от коммерческой конфигурации.

## 15. Экспорт, редактирование и сопровождение

Экспорт JSON: версия схемы, параметры, материалы, шаблоны, список выбранных услуг. Без контактов и данных объекта, не нужных для геометрии. Импорт валидируется и ограничивается по размеру; неизвестная версия даёт объяснение, не вызывает падение.

Если нужен реальный файл по одной кнопке, серверная генерация PDF — отдельная задача следующего этапа. Не называть браузерную печать готовым автоматическим КП.

В экспорт включать фразу «Предварительная компоновка», единицы, версии шаблона/прайса и исключения. Экспорт не обозначается как КМ/КМД и не содержит штамп рабочего проекта.

Содержание, контакты, перечень услуг, видимость материалов и тарифы редактируются через файлы конфигурации. Контакты заполняются по topengineer.ru/contact согласно разделу 2.1 и единообразно используются во всех блоках и экспорте. Каждое поле описано в README. Для первоначального сайта CMS не обязательна. Если сотруднику нужен редактор без Git, это отдельное расширение со входом, ролями и журналом изменения тарифов.

## 17. Производительность, инфраструктура и безопасность

Контрольные ширины: 360, 390, 768, 1280, 1440 px. Проверять актуальные Chrome/Edge на Windows, Firefox, Safari/iOS и Chrome/Android. Конкретные версии записать в отчёт приёмки.

Цели основных Web Vitals: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 по полевым данным при достаточном трафике. До запуска — лабораторная проверка с зафиксированным устройством и сетью; оценки Lighthouse не приравнивать к реальным полевым данным. Бюджет первичного JS без 3D — ориентир ≤200 КБ gzip, изображение первого экрана ≤250 КБ, шрифты локально. Изменения бюджета обосновать измерением.

Размещение: сервер приложения и база заявок в РФ, HTTPS, закрытый административный доступ, резервное копирование, проверенная процедура восстановления. Домен и провайдера выбирает владелец. Не делать зарубежный сервис форм единственной точкой сохранения заявок.

Секреты через переменные окружения; `.env.example` без значений. Staging закрыт от индексации. Production не содержит демонстрационных телефонов, тарифов, кейсов и заглушек юридических документов.

Проверка настроек: отсутствие секретов в клиентском bundle, ограничение размера запроса, экранирование пользовательского контента, защита файлового хранилища, отсутствие персональных данных в URL/analytics, период хранения логов и резервных копий. Эти проверки относятся к реальной форме сайта, а не к декоративным блокам.

Работать этапами: структура и дизайн → геометрия и ведомость → 3D базовых форм → комплекс по альбомам → коммерческий расчёт → реальные заявки → расширенные формы → приёмка и запуск. Подробные задания находятся в `CODEX_PLAN.md`.

**Обязательное разбиение для работы с лимитами:** 12 крупных этапов разделены в плане на 32 небольших блока с ID. Один запрос на выполнение охватывает один блок; большой блок делится дополнительно до существенных правок. После завершения блока сохранять проверенную версию и журнал, затем завершать запрос. Следующий блок запускается отдельным заданием.

До правок записать текущий ID, исходную проверенную версию, намеченные файлы, проверки и следующий шаг. Обновлять запись по ходу работ, а не только в финальном сообщении. После прерывания сначала сверить журнал с реальными файлами, Git и состоянием ранее запущенных команд, затем завершить незаконченный блок. Запрещено начинать проект заново, уничтожая промежуточные изменения.

Незавершённая работа ведётся в отдельной ветке; последний проверенный код и размещённый сайт сохраняются. Промежуточный WIP не считается проверенной версией. Лимит может оборвать работу до сборки или обновления журнала, поэтому непрерывная исправность рабочей ветки не гарантируется; сохранность принятых блоков обеспечивается версиями Git и резервными копиями. Проверить восстановление из файлов проекта без истории чата в B11.3. Полный порядок — в разделе «Сохранение прогресса и восстановление после лимита» плана.

Рекомендуемая основная модель — **GPT-6.1 Sol, Medium, Standard**, если она доступна в аккаунте. Для коротких самостоятельных правок текста, CSS и конфигураций — **GPT-6 Luna, Low/Medium**. Сложные геометрические ошибки и ревью расчётного модуля — Sol High на отдельном этапе. Astra не требуется как постоянная модель проекта.

Это рекомендация по качеству и расходу, а не гарантия завершения в одном лимите. [Официальная документация OpenAI](https://learn.chatgpt.com/docs/models) рекомендует Sol для сложной разработки, Luna для ограниченных повторяемых задач; более высокое усилие рассуждения увеличивает расход токенов.

По [тарифной таблице Codex](https://learn.chatgpt.com/docs/pricing) ставки платных кредитов Luna существенно ниже Sol; пересчитывать эти ставки в число включённых задач Plus нельзя. [Fast](https://learn.chatgpt.com/docs/agent-configuration/speed) расходует включённые лимиты быстрее Standard. Использовать Standard для экономии.

Практический объём: 12 этапов, 32 блока и необходимые исправления; первый предметный прототип охватывает этапы 1–5. Число обращений может быть больше числа блоков при остановках или дополнительном разбиении. Не обещать «хватит ровно N токенов» или «один блок всегда помещается в лимит»: повторное чтение файлов, история, инструментальные результаты и рассуждения также входят в расход.

Сайт не нуждается в OpenAI API во время работы: все калькуляторы детерминированные. Модель используется для разработки и поддержки, а не для вычисления цены в каждом запросе посетителя.

# Общедоступный просмотр для коллеги (5 октября 2026)

По явному запросу владельца существующий GitHub становится public. Для оценки
сайта в браузере без установки программ используется GitHub Pages с отдельной
статической сборкой: 3D-конфигуратор, цена RUB, каталог, изображения и обе формы.
GitHub Pages не запускает POST API: формы в этой демонстрации явно не отправляют
заявки и не сообщают об их сохранении. Локальная/portable работа не меняется.
Публичный коммерческий приём заявок требует серверного хостинга и настройки.
История main сохраняется; .env, локальные заявки и базы не публикуются.
