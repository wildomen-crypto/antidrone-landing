# Эксплуатация и публичный запуск

Локальная версия слушает 127.0.0.1:3100. Внешнего сервера и домена в задаче
нет; эти инструкции подготовлены для следующего этапа. Публикация не выполнена.

## Перед запуском

1. Подтвердить оператора формы и сторону договора. Обновить company.formOperator,
   config/legal.ts и оба правовых документа: цели, основания, права, сроки,
   обработчики, размещение и порядок работы с резервными копиями.
   После утверждения изменить версию согласия и legal.approved.
2. Сверить config/company.ts с https://topengineer.ru/contact.
   Не смешивать реквизиты разных организаций. Утвердить материалы и тексты.
3. Согласовать допустимые конструктивные сочетания, профили и условия заказа.
   Пока нет утверждённых тарифов, оставить ручную стоимость.
4. Выбрать сервер и частное хранилище БД в РФ, домен, HTTPS и получателя заявок.
   Статический HTML-хостинг не обеспечивает SQLite и серверную форму.
5. Настроить постоянный DATA_DIR вне каталога заменяемого релиза. Доступ —
   только процессу сайта и уполномоченному оператору. БД не класть в public.

## Размещение приложения

Установить поддерживаемый Node.js 24 и npm на выбранном сервере.
Зависимости и сборка — по package-lock.json:

```text
npm ci
npm run check
```

build дополнительно создаёт .local/runtime для административной CLI.
Этот каталог служебного кода должен входить в серверный релиз вместе с
scripts/leads.cjs; данные DATA_DIR переносятся отдельно.

Настройки среды:

```text
DATA_DIR=/srv/topengineer-data
SITE_PUBLIC=true
SITE_ORIGIN=https://ВАШ-ДОМЕН
TRUST_PROXY=true
NOTIFICATION_WEBHOOK_URL=УТВЕРЖДЁННЫЙ-АДРЕС-ПОЛУЧАТЕЛЯ
NOTIFICATION_WEBHOOK_TOKEN=СЕКРЕТ
```

Примеры путей и домена заменить реальными значениями. Секреты хранить в
защищённом файле среды службы, отдельно от Git. На Windows аналогично
использовать постоянный каталог с ограниченными ACL.

Запускать Next через менеджер служб, от отдельного пользователя:

```text
node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3100
```

Перед ним настроить HTTPS reverse proxy. Он должен передавать корректный
Host, перезаписывать X-Forwarded-For, ограничивать размер запросов,
не предоставлять доступ к DATA_DIR/.local/.env и журналировать без тела
заявок. Без собственного proxy оставить TRUST_PROXY=false; тогда лимит
запросов общий для прямых подключений. SITE_ORIGIN определяет origin
формы независимо от внутреннего адреса Next.

## Заявки и очередь

На локальном компьютере:

```powershell
npm.cmd run leads -- status
npm.cmd run leads -- list
npm.cmd run leads -- export НОМЕР-ЗАЯВКИ C:\ЧАСТНЫЙ-КАТАЛОГ\заявка.json
npm.cmd run leads -- delete НОМЕР-ЗАЯВКИ
npm.cmd run leads -- worker
npm.cmd run leads -- retry-failed
npm.cmd run leads -- backup C:\ЧАСТНЫЙ-КАТАЛОГ\backup-ДАТА.sqlite
```

status показывает количества; list — номера, даты и версии согласия.
export сохраняет данные только в явно указанный новый файл. Не направлять
экспорт в публичный каталог. Права на каталог и файлы задаёт владелец сервера.
Удаление выполнять по проверенному обращению заявителя.

В службе использовать предварительно собранную CLI:

```text
node scripts/leads.cjs worker
```

Настроить её запуск каждые 1–5 минут штатным планировщиком сервера, с той же
средой DATA_DIR и секретами. Сама эта задача планировщика здесь не создана.
worker удаляет истёкшие записи и отправляет очередь. Пять неудачных попыток
переводят запись в failed; проверить получателя и выполнить retry-failed.
Увеличивающаяся очередь и failed должны контролироваться оператором.

Webhook получает только leadId. Idempotency-Key стабилен при повторной
доставке. Для получения полных данных нужен частный корпоративный адаптер
или экспорт через CLI; не добавлять незащищённую выгрузку на сайт.
SMTP/CRM не подключены без фактических настроек владельца.

## Резервные копии

Исходный код: git bundle и git archive; в них не включаются .env и заявки.
БД: команда backup использует согласованный снимок SQLite с учётом WAL.
Обычное копирование одного работающего leads.sqlite может пропустить данные.

Резервировать частный каталог вне public; ограничить доступ, определить
сроки хранения и удаление копий. После создания проверить integrity_check
и восстановление в отдельный частный каталог с новым DATA_DIR.
Служба должна быть остановлена перед заменой рабочей БД; текущую рабочую
версию сначала сохранить. Здесь не выполнялась замена базы владельца.

## Приёмка и обновления

Провести заявку через HTTPS: согласие, сохранённый ID, очередь/получатель,
повторная отправка, работоспособность телефонов и email. Проверить реальные
мобильные устройства, редакцию документов и резервное восстановление.
Затем включить индексацию в app/layout.tsx, добавить канонический URL,
sitemap/robots для реального домена и согласованную аналитику при необходимости.

Хранить предыдущий проверенный релиз. Новый собирать в отдельном каталоге;
DATA_DIR сохранять постоянным. До переключения выполнить typecheck, unit,
build и локальную браузерную QA. Откат кода не должен удалять SQLite и секреты.

Записать в STATUS.md домен, версию, дату, процесс, результаты сквозной заявки
и место частных резервных копий — без значений секретов и контактов заявителей.
